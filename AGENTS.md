## Архитектурные границы

- Модульный монолит: Python 3.12, FastAPI, PostgreSQL 17, SQLAlchemy 2, psycopg 3, Alembic.
- Простой фронт: Jinja2, CSS, vanilla JavaScript, нативный HTML5-плеер. Русский интерфейс с компоновкой YouTube.
- Четыре постоянных сервиса: Nginx, API, PostgreSQL, Python-worker. API и worker используют один образ.
- Задания хранятся в PostgreSQL; видео — в постоянном файловом томе. Результат обработки — один MP4 до 720p и превью.
- Не добавляй SPA, Redis, Celery, S3, HLS или новый постоянно работающий сервис без конкретной необходимости в текущей задаче. Если потребность возникла, сначала объясни изменение принятой архитектуры.
- HTTP-маршруты тонкие; правила и транзакции находятся в сервисах. HTML и API используют одни правила доступа.
- Синхронный ORM и файловый I/O не блокируют event loop. Не удерживай транзакцию или соединение БД во время загрузки, FFmpeg и раздачи видео.

## Инварианты, которые нельзя нарушать

- Приватность, модерация и обработка — независимые состояния. Worker не меняет приватность и не восстанавливает скрытое видео.
- Роли moderator/admin не дают автоматического просмотра приватного видео.
- Проверяй доступ также к превью, MP4, HEAD и Range; фильтруй недоступные записи до пагинации и подсчёта.
- Сначала проверяй права и квоты, затем читай тело загрузки. Не загружай большой файл целиком в память.
- READY устанавливается только после проверки и публикации результата текущей попытки; повторное выполнение и падение worker не создают дубли.
- Новые запросы после отзыва доступа запрещены. Уже начатую передачу и полученные байты отозвать нельзя; не обещай обратное.
- Пароли, токены, приватные файлы и реальные секреты не помещай в логи, тестовые отчёты и архив.

## Рабочий процесс

1. Прочитай требования и документы, относящиеся к изменению; исследуй существующий код через rg и точечные чтения.
2. Выбери минимальную законченную вертикаль с проверяемым результатом. Не расширяй продукт за пределы задания.
3. Для нетривиальной работы используй подходящий навык из .agents/skills. Для небольшой правки отдельный процесс не нужен.
4. Меняй API, схемы, миграции, UI и документацию согласованно. Ограничения целостности закрепляй в PostgreSQL.
5. Запусти проверки, соответствующие изменению. При сбое исправь причину; не ослабляй проверку ради зелёного результата.
6. После этапа обнови docs/status.md: сделано, реально выполненные проверки, ограничения, следующий шаг. Секреты туда не записывай.
7. В ответе кратко укажи результат и проверки; невыполненные проверки называй прямо.

Авторизованную обратимую работу выполняй без повторных согласований. Не удаляй чужие изменения и реальные данные. Не меняй глобальные настройки Codex и не публикуй проект без соответствующей задачи.

## Делегирование

- Главный агент отвечает за архитектуру, интеграцию и итоговый результат.
- foxtube_fullstack — API, PostgreSQL, шаблоны и пользовательские сценарии.
- foxtube_video — загрузка, файловое хранение, очередь, FFmpeg и раздача.
- foxtube_security — независимое ревью авторизации, приватности, загрузок и конфигурации; без редактирования файлов.
- foxtube_qa — проверки поведения, браузерные сценарии и приёмка; исправления приложения возвращает разработчику.
- Делегируй содержательные независимые задачи. Давай цель, контекст, разрешённые файлы и критерий завершения. Один файл одновременно редактирует один исполнитель.
- Агентам не передавать фиктивные результаты проверки. Нет доступного специалиста — выполни его проверку сам и укажи это.
- Не более трёх дочерних агентов одновременно; вложенное делегирование не использовать. Модель и права наследуются от основной сессии.

## Проверки и готовность

- Каркас запускается командой `bash scripts/bootstrap.sh` (`make up`); на чистой Ubuntu 24.04 — `sudo bash scripts/bootstrap.sh`. Перед изменением сверяй фактические ограничения в docs/status.md.
- `make check` — Ruff, mypy, ShellCheck и unit-тесты в development-образе; `make test` — изолированный Compose с настоящими PostgreSQL/Nginx. Обвязка: `make agents-check`, `make doctor`.
- Python-зависимости зафиксированы в uv.lock. При изменении pyproject.toml обновляй lock через Python 3.12/uv и проверяй сборку --frozen; инструменты разработки не включай в runtime-окружение.
- Интеграционные проверки используют настоящий PostgreSQL; проверка медиа проходит через Nginx; видеотест запускает настоящий FFmpeg.
- H.264 проверяется Playwright с Google Chrome в тестовом окружении, включая продвижение currentTime и перемотку.
- `make test-browser` — изолированный Chrome, загрузка через экран, настоящий FFmpeg, воспроизведение и перемотка; снимки/отчёт в .artifacts/video-browser.
- Не добавляй тесты, проверяющие только текст реализации. Для исправления ошибки предпочитай воспроизведение исходного дефекта.
- Значимое изменение авторизации или медиа должно получить проверку безопасности; завершённая вертикаль — проверку QA. Маленькая документационная правка этого не требует.
- Функция готова, когда выполнен связанный критерий TestTask.md, проверки прошли, а инструкции запуска и состояние актуальны.

## Code Review Rules

Ищи нарушения доступа, гонки состояний, утечки файлов, блокирующий I/O, потерю заданий и невоспроизводимый запуск. Для замечания указывай серьёзность, файл/строку, условие возникновения и последствия. Отделяй подтверждённый дефект от гипотезы; замечания по стилю оставь линтеру.

## Общение

Отвечай по-русски и кратко. Код, документация и сообщения коммитов — обычным точным языком. Пиши, что проверено; не утверждай, что приложение готово, по результатам одной проверки конфигурации.
