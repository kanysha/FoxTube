# Комплексная проверка FoxTube — 2026-11-04

Проверялись весь проект по TestTask.md, полный пользовательский путь и отдельно
приватное видео с двумя получателями, выбранными владельцем. Найден один
подтверждённый дефект приложения: неверное выделение «Мой канал» на чужом канале.
Исправлен. Нарушений приватного доступа в выполненных сценариях не обнаружено.
Последующая установка на чистую Ubuntu 22.04.5, повторный bootstrap,
перезагрузка ВМ и Chrome/private прошли: [отдельный протокол](review-ubuntu-2026-11-04.md).
Полная приёмка поставки остаётся открытой из-за нагрузки на целевом сервере
и финальной комплектации. Ниже сохранены результаты исходного локального прогона.

## Окружение и доказательства

- macOS, Docker Desktop/Engine 29.7.2, Compose 5.4.0; Docker видит 10 CPU и
  8 319 504 384 байт RAM. Это не выделенный сервер 4 CPU/8 ГБ.
- Приложение и проверки работают на Python 3.12 из образа; PostgreSQL 17,
  настоящий FFmpeg/ffprobe, раздача через Nginx. Chrome — отдельный контейнер.
- Каждый интеграционный, браузерный, аварийный и нагрузочный запуск получает
  собственный Compose-проект, случайные секреты, порт и временные тома.
  Действующий локальный проект и его данные не удалялись.
- Логи находятся в `.artifacts/comprehensive/`, JSON и снимки — в
  `.artifacts/video-browser/`, `.artifacts/resilience/`, `.artifacts/capacity/`.
  Они исключены из Git. Пароли, cookie и токены в отчёт не включены.

## Полный пользовательский путь

В Chrome создан новый аккаунт, через экран загружен новый настоящий H.264/AAC-файл.
Worker получил READY, плеер реально воспроизводит видео: проверяются продвижение
`currentTime`, переход на 7-ю секунду и дальнейшее воспроизведение. Через экран
поставлен лайк, опубликован экранированный комментарий, создан плейлист; состояние
проверяется после перезагрузки. Второй аккаунт подписался на автора и отправил жалобу.

Через UI проверены назначение модератора, скрытие/восстановление видео, закрытие
жалобы, аудит и запрет понижения последнего admin. При скрытии новые HEAD/Range
запросы запрещены; после восстановления снова работают. Проверяются поиск, канал,
1440×900 и 390×844. Swagger проверяется через настоящий Try it out:
метаданные 201 → бинарная загрузка 202 → READY → воспроизведение.
В финальном прогоне Chrome 156.0.8078.80: время плеера 1,008 → seek 7 → 8,014 с;
длительность 10,008 с. У получателей private-видео после перемотки 8,026 и 8,025 с;
у Swagger-видео время продвинулось до 1,023 с. Исключений JavaScript нет.
Независимая визуальная QA свежих снимков прошла: чужой канал, private-владелец
desktop/mobile и private-получатель desktop. В мобильном виде доступны кнопки
выдачи/отзыва, горизонтального переполнения нет. Снимок private-получателя на
mobile не создавался; его отдельная визуальная проверка не выполнена.

## Приватное видео и узкий круг получателей

Создано отдельное private-видео через экран загрузки. Владелец через UI выдал
доступ двум зарегистрированным адресатам; список сохранился после reload.
Используются независимые браузерные сессии владельца, двух получателей,
постороннего аккаунта и гостя.

| Кто | До отзыва | После отзыва только у первого получателя |
|---|---|---|
| Владелец | Просмотр, управление видео и разрешениями | Сохраняются |
| Первый получатель | Страница, API, превью, MP4; реальный просмотр и перемотка | Новые запросы к странице/API/медиа/социальным действиям запрещены |
| Второй получатель | Те же права просмотра | Продолжает реальный просмотр и перемотку |
| Посторонний и гость | 404 для закрытых объектов и медиа | По-прежнему 404 |
| Moderator/admin без разрешения | Приватное видео не открывается (интеграционные тесты) | Роль не обходит ACL |

Для превью и MP4 проверены GET, HEAD и Range через Nginx, а также `no-store`.
Проверены метаданные, HTML, социальные счётчики и комментарии. Недоступные записи
исключаются из поиска, канала, счётчиков и публичного плейлиста до выдачи результата.
Получатель не может читать список разрешений, выдавать доступ или сделать ролик
публичным. Отзыв одного разрешения не затрагивает другого получателя.

Уже полученные байты и начатую передачу отозвать нельзя. Проверка отзыва относится
к новым запросам; прекращение уже буферизованного воспроизведения не обещается.

## Память и локальная нагрузка

Передано ровно **524 288 000 байт (500 МиБ)** без полного буфера на клиенте.
Это реальное 45-секундное видео с валидным MP4 free box: проверяется память
потоковой загрузки, а не наиболее тяжёлое декодирование 500 МиБ видеокадров.
Одновременно наблюдались две активные передачи, реальный FFmpeg и 10 HTTP-зрителей.

- Суммарный RSS Python-процессов API: **268,92 → максимум 289,59 МиБ**;
  рост **20,66 МиБ**, 65 измерений.
- Зрители выполнили **2091** запрос Range по 64 КиБ, получили 137 035 776 байт;
  все ожидаемые ответы — 206. Максимальная измеренная задержка запроса — 77 мс.
- Все три новых ролика достигли READY; сценарий занял 50,07 с.

Это smoke-проверка в Docker Desktop, а не измерение максимальной ёмкости/SLA.
Зрители — HTTP-клиенты с диапазоном каждые 200 мс, не десять полноценных браузеров.
Внешний канал, выделенные 4 CPU/8 ГБ и длительная нагрузка не проверены.

## Найденные проблемы и исправления

| ID | Серьёзность и воспроизведение | Исправление и проверка |
|---|---|---|
| UI-01 | P3. Войти зрителем и открыть чужой канал: боковое меню выделяет «Мой канал», хотя открыт канал автора | `app/web/routes.py:218`: выделение только при `info.can_manage`. Браузерный сценарий проверяет чужой канал без выделения и переход на собственный с выделением; финальный повтор passed |

Отдельно исправлены проблемы тестовой обвязки; это не дефекты доступа FoxTube:

- Первый расширенный Chrome-прогон завершился `Target crashed` при создании
  дополнительных приватных контекстов. В изолированном browser-сервисе поднят
  лимит процессов 256 → 1024. Полный повтор прошёл; приложение не ослаблялось.
  Точная причина падения Chrome на уровне ОС отдельно не трассировалась.
- Первый аварийный прогон прошёл три аварии, но тест рестарта обращался к старому
  случайному порту Docker. Клиент перечитывает порт после рестарта; все четыре
  сценария затем повторены успешно.
- P2, новая обвязка: при ошибке на открытом Swagger аварийный скриншот мог
  сохранить CSRF из curl. В `tests/browser/run.py:407` curl/request snippets
  маскируются; успешный снимок сохраняется после сворачивания операций.
  Риск подтверждён независимым статическим security-ревью, фактической утечки
  не зафиксировано.
- P2, новая обвязка: ошибка до запуска передач могла оставить фоновых зрителей
  работающими и заблокировать завершение нагрузочного теста. В
  `tests/resilience/capacity.py:190` остановка потоков находится в общем `finally`.
  Исправление подтверждено независимым security-ревью; успешный нагрузочный
  прогон завершился без зависания.

Независимое статическое security-ревью проверило реальные пути ACL до SQL/Nginx,
сессии/CSRF, права SQL-ролей, публикацию результата, устаревшую аренду и обработку
недоверенных файлов. Открытых подтверждённых P0–P3 в просмотренном приложении
после исправления UI-01 нет. Это границы выполненного анализа, не гарантия
отсутствия любых уязвимостей.
После всех прогонов в Docker остались только четыре исходных контейнера FoxTube
(healthy); временных Compose-проектов тестов, их томов и сетей нет.
