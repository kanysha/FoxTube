# Принятая архитектура FoxTube

Статус: реализованы каркас, учётные записи, видеоконвейер, каналы, социальные
действия, модерация, роли и демо. Оставшиеся проверки —
в [roadmap.md](roadmap.md), результаты проверок — в [status.md](status.md).
Документ фиксирует упрощение плана FoxTube.md от 2026-11-03. Требования — в [TestTask.md](../TestTask.md).

## Компоненты и зависимости

- Python 3.12, FastAPI, Pydantic 2, Uvicorn; PostgreSQL 17, SQLAlchemy 2, psycopg 3, Alembic.
- Jinja2, CSS, обычный JavaScript; HTML5 video. Интерфейс на русском, адаптивная компоновка YouTube.
- Четыре постоянных сервиса: Nginx, API, PostgreSQL, Python-worker. API и worker — один образ, разные команды.
- Локальный постоянный медиатом: API/worker имеют необходимые права записи, Nginx — только чтение. PostgreSQL хранит метаданные и очередь.
- Очередь не использует Redis/Celery/отдельный диспетчер. Выход не использует HLS и hls.js. Таблица сегментов/video_assets не нужна.
- Версии Python-зависимостей фиксируются в uv.lock; образы — конкретными версиями/digest с плановым обновлением безопасности.
- Роутер → сервис → SQLAlchemy/локальное хранилище. Сервисы общие для HTML и JSON. Универсальные фабрики и репозитории не нужны.

## Модули и данные

Сейчас реализованы app/core (настройки, соединения, защитные заголовки), app/health,
app/auth (схемы, модели, сервисы, пароли, сессии, CSRF и ограничение частоты),
app/videos (модель, сервис доступа, потоковая загрузка, хранилище, очередь,
FFmpeg, JSON и медиа), app/channels (профиль и доступные видео автора),
app/social (лайки, комментарии, подписки, плейлисты), app/moderation
(жалобы, роли и аудит), app/web (HTML/ресурсы), app/demo.py и app/worker.py.
Таблицы: service_heartbeats, users, channels, sessions, auth_rate_limits,
videos, video_jobs, video_grants, likes, comments, subscriptions, playlists,
playlist_items, reports, audit_events; Alembic также ведёт alembic_version. Регистрация атомарно
создаёт пользователя, один канал и сессию, отзывая прежнюю сессию.
Worker обновляет heartbeat, обрабатывает видео и раз в минуту очищает
auth-данные, истёкшие резервы, удалённые файлы и остатки незавершённых попыток.
Readiness проверяет PostgreSQL, совпадение миграций, свежий heartbeat и доступность медиатома.

Миграции, deploy, scripts, tests находятся отдельно. Защищённая раздача
находится в videos/routes.py и не требует отдельного media-сервиса.

В videos хранятся внутренние ключи исходника, результата и превью, параметры файла,
владелец и независимые состояния обработки, видимости и модерации.
video_jobs хранит технические поля исполнения; состояние публикации находится в videos.

UUID, внешние ключи, timestamptz. Ограничения уникальности: нормализованный email,
handle канала, пары лайка/подписки/разрешения и видео в плейлисте.
Один канал на пользователя. Поиск названия — ILIKE и GIN pg_trgm.
Приватный доступ: владелец вводит точный email зарегистрированного пользователя;
video_grants связывает video_id и user_id. Неизвестный email не создаёт приглашение.
Списки: 20 элементов по умолчанию, максимум 50; ACL в SQL до пагинации/счётчиков.
Агрегации пакетные, без N+1 и перемножения лайков с комментариями.

Лайк, подписка и добавление в плейлист используют PUT/DELETE и уникальные пары
в PostgreSQL: повторные и конкурентные запросы не создают дублей. Комментарий
удаляет его автор или владелец видео. Плейлист меняет только владелец;
private-плейлист не имеет получателей доступа. Его public/private не меняет
ACL содержащихся видео. Канал показывает только доступные плейлисты и видео;
лента подписок использует ту же политику readable.

Изменения, зависящие от доступа к видео, сначала блокируют строку Video, затем
повторно проверяют ACL отдельным запросом. Это важно при READ COMMITTED: запрос,
ожидавший блокировку, мог начать работу до отзыва grant. Квоты социальных
действий сериализуются по пользователю; блокировки держатся только в короткой
транзакции, без HTTP и FFmpeg.

Жалобы, скрытие/восстановление и смена ролей проходят через ограниченные
SECURITY DEFINER-функции PostgreSQL с фиксированным search_path. Runtime API
не получает прямого UPDATE роли/модерации и INSERT/UPDATE аудита. Общая
транзакционная advisory-блокировка сериализует смену роли и модерацию;
роль проверяется после её получения. Назначение роли и аудит атомарны,
понижение последнего admin запрещено. Первый admin назначается отдельной
локальной CLI-командой с ролью миграций существующему аккаунту.
Журнал фиксирует жалобы, решения, скрытие/восстановление и смену ролей;
изменения владельцем privacy/grants в этот журнал пока не входят.

## Учётные записи и сессии

JSON и HTML используют app/auth/service.py и общие зависимости доступа.
Синхронные запросы PostgreSQL и Argon2 выполняются вне event loop; во время
хеширования соединение БД не удерживается. Пул ограничен; тяжёлых операций
Argon2 не более двух на процесс API. Изменения сессии блокируют её строку
FOR UPDATE и повторно проверяют срок/отзыв, поэтому из двух одновременных
попыток ротации проходит одна.

Случайная cookie хранится только у клиента, в sessions — SHA-256 токена.
CSRF вычисляется HMAC с ключом текущей cookie; отдельный секрет в настройках
не нужен. Сессии фиксированного срока: анонимная 30 минут, после входа 7 суток.
Пользователь и роль читаются из БД при запросе. Ограничители частоты общие
для процессов, через UPSERT в PostgreSQL; неудачные попытки также фиксируются.
Worker удаляет до 500 старых сессий и 500 истёкших ограничителей за проход.
Подробные параметры и права — в [security.md](security.md).

## Контракты и загрузка

- JSON API: /api/v1; Swagger: /docs, локальные ресурсы, рабочие сессии и CSRF.
- POST /api/v1/videos: метаданные и ожидаемый размер, создание черновика.
- PUT /api/v1/videos/{id}/source: application/octet-stream; в OpenAPI явно описать бинарное тело.
- До тела: авторизация, владелец, CSRF, атомарное резервирование квоты/места/слота.
- Один зарезервированный черновик на пользователя, пять минут для начала
  передачи; начатая передача — до 30 минут с обновляемой арендой. Создание
  черновиков ограничено 10 попытками на пользователя и 20 с IP за 15 минут.
- Request.stream() пишет ограниченными блоками; реальный размер проверяется независимо от заголовков. Никакой полной загрузки в RAM и дополнительного multipart-spool.
- Для этого маршрута Nginx proxy_request_buffering off и proxy_http_version 1.1.
- Частичный файл → атомарное переименование на том же томе → транзакция QUEUED + задание → 202. Разрыв связи БД/файловой системы закрывает очистка остатков.
- Повторная передача после успешного принятия не создаёт второе задание. Прерванная передача повторяется целиком.
- XHR показывает отправку; опрос каждые 2 секунды — очередь/обработку. 100% готовности только после READY.
- Медиа: GET/HEAD /media/videos/{id}/playback и /poster, проверка прав → Nginx X-Accel-Redirect в internal location; Range обрабатывает Nginx.

## Видео и очередь

Вход: MP4/MOV/WebM с разрешёнными декодерами, до 500 МиБ, 20 минут,
1080p (1920×1080 или 1080×1920), до 60 fps.
Выход: один MP4 H.264/yuv420p, AAC до 128 Кбит/с стерео при наличии звука,
до 30 fps, faststart. Вписывать в 1280×720 или 720×1280, без увеличения,
с учётом поворота, пропорций и чётных размеров. JPEG-превью из видео.
Кодирование: libx264, veryfast, CRF 23, maxrate около 2,5 Мбит/с с заданным bufsize.
Только основной видеопоток и необязательный аудиопоток; вложения и лишние метаданные не переносить.

UPLOADING → QUEUED → PROCESSING → READY/FAILED. При временной ошибке — возврат в очередь.
Один worker, одно перекодирование, опрос 2 секунды. Получение задания через
FOR UPDATE SKIP LOCKED в короткой транзакции; аренда 120 секунд, продление во
время кодирования каждые пять секунд, heartbeat простаивающего worker — 10 секунд,
идентификатор попытки, до трёх попыток только для временных ошибок.
ffprobe — тайм-аут 30 секунд; кодирование — максимум 30 минут на попытку.
После потери аренды/связи с БД завершить FFmpeg; при остановке worker завершить и собрать дочерний процесс.
Контейнер использует init и restart policy. Каждая попытка пишет в свой каталог.
Готовые файлы закрываются, проверяются и атомарно публикуются; READY фиксируется
только текущей попыткой, если видео не удалено. Worker не меняет visibility/moderation.
Опубликованные ключи содержат идентификатор попытки; медиа берётся только по ключу,
зафиксированному в videos текущей попыткой. Устаревшая попытка не перезаписывает активный файл.

Исходник удалить после успешной фиксации READY. Неудачные исходники хранить
до 24 часов; незавершённые загрузки/резервы имеют ограниченный срок и очистку.
Удаление видео сначала логическое с немедленным запретом новых запросов,
затем физическое в worker. Повторный запуск не воскрешает удалённый объект.

## Бюджет ресурсов и поставка

- Сервер: 4 CPU / 8 ГБ RAM; worker максимум 2 CPU / 2 ГиБ, FFmpeg до двух потоков. API — два процесса с ограниченным пулом БД.
- Максимум две одновременные передачи на сервер и одна на пользователя; очередь до 20 ожидающих с учётом резервов.
- Квота 5 ГиБ на пользователя: вход, результат и зарезервированное место. Неприкосновенный свободный остаток — 5 ГиБ.
- Длительный I/O не удерживает транзакции/соединения. Синхронный ORM выносится из async event loop.
- Служебные файлы/логи ограничены по объёму; очистка выполняется тем же worker.
- Runtime API и worker работают от UID 1000, с read-only корневой ФС, отдельными ролями БД и ограничениями ресурсов. Схему меняет одноразовый migrate; он не является пятым постоянным сервисом.
- Nginx публикует единственный порт; БД/API на хост не публикуются. Медиа доступны только через internal location. Docker DNS повторно разрешает адрес API после его пересоздания.
- Один MP4 означает отсутствие адаптивного качества. Десять потоков по 2,5 Мбит/с требуют примерно 25 Мбит/с исходящего канала.
- Целевая установка: Ubuntu 22.04 и 24.04 LTS, от 40 ГБ свободного диска;
  sudo bash scripts/bootstrap.sh [--demo]. Проверена чистая Ubuntu 22.04.5: [протокол](review-ubuntu-2026-11-04.md). Ubuntu 24.04 отдельно не проверялась.
- Повторный bootstrap/seed сохраняет данные и секреты. Демо: 6 аккаунтов, 12 подготовленных коротких MP4 с разной доступностью и социальными данными.
- HTTP-демо слушает 127.0.0.1:8080; удалённая проверка через SSH-туннель. Публичное размещение требует HTTPS.

Демо — отдельная явно вызываемая команда, без дополнительного сервиса. Она
создаёт MP4 через FFmpeg, регистрирует обычные аккаунты и передаёт файлы
по HTTP через Nginx, ожидая READY от настоящего worker. Постоянный manifest
с паролями имеет 0600, отдельную блокировку и атомарное сохранение;
повтор использует записанные IDs. Seed не назначает роли, не очищает существующую
БД и не восстанавливает удалённые вручную демо-комментарии.

Прямые эфиры, Shorts, адаптивный стриминг, распределённое размещение,
возобновляемые загрузки и почтовые приглашения вне первой версии.
