# Ubuntu: доступ из локальной сети

Дата: 2026-11-05. Задача — установка одной командой, доступ только к приложению
из подключённой локальной подсети, сохранение после reboot и безопасный повтор.
Это проверка LAN-развёртывания и основных функций, а не полная приёмка поставки.
Итог: **passed** на чистой и существующей Ubuntu 22.04.5; приложение работает по
`http://192.168.1.16:8080`. Открытых подтверждённых дефектов в проверенной области
не осталось; непроверенное перечислено ниже.

## Окружение и исходное состояние

Проверялась выбранная пользователем Ubuntu 22.04.5, kernel 5.15.0-202-generic:
ВМ501 на Proxmox, 4 vCPU/8196 МиБ, диск 100 ГБ. Адрес `192.168.1.16/24`,
интерфейс ens18. Внешние HTTP/TCP-запросы выполнялись с другого компьютера.

До изменения Docker публиковал только Nginx на `127.0.0.1:8080`, поэтому сайт
не открывался по LAN IP. PostgreSQL:5432 и API:8000 уже не публиковались.
Redis в проекте отсутствует. UFW был inactive, SSH:22 доступен; Docker использовал
iptables-nft, общий nftables.service был disabled.

Сохранён полный cold snapshot `foxtube-before-lan-20261105` до любых изменений ВМ.
Он содержит существующие данные: 22 пользователя, 20 видео, по 10 лайков,
комментариев и плейлистов, 6 разрешений и 40 MP4/JPEG. Для чистых попыток
использован прежний снимок `foxtube-clean-20261104` без Docker и проекта.

## Что изменилось

```bash
sudo bash scripts/bootstrap.sh
```

На Ubuntu команда выбирает назначенный частный IPv4 основного интерфейса,
согласует bind/public origin и публикует единственный TCP-порт Nginx, обычно 8080.
Для выбора интерфейса предусмотрен `--lan-ip ADDRESS`; `--no-lan` пропускает
управление сетью и не удаляет существующие правила.

Новый `scripts/configure_lan.py` проверяет итоговый Compose, локальный Docker,
конфликты слушателей и управляемых файлов. Пользовательские нестандартные
bind/origin, чужие правила и работающий LAN endpoint с другим IP/портом
сохраняются с отказом, а не перезаписываются.

Таблица `inet foxtube_lan` отбрасывает обращения к IP/порту приложения с источником
вне `192.168.1.0/24` в prerouting с приоритетом -110, до Docker DNAT.
Остальной трафик и чужие таблицы не меняются. UFW не включается и не сбрасывается;
настройки SSH не редактируются. PostgreSQL и API остаются только внутри Docker.

Правила `/etc/foxtube/lan.nft` применяет включённая oneshot-служба
`foxtube-lan-firewall.service`. Docker зависит от неё при загрузке. Повтор
атомарно заменяет только собственную таблицу через reload, без рестарта dockerd.
Глобальный nftables.service с системным `flush ruleset` не включается.

## Обновление существующей ВМ

После успешной чистой приёмки восстановлен снимок рабочей ВМ. До обновления
подтверждены исходные counts и хеши. Заменены только исходники проекта;
.env, секреты и постоянные тома не переносились из чистой установки.

На исходных данных прошли bootstrap, повтор и настоящая перезагрузка ОС.
После каждого шага внешний HTTP/TCP-probe прошёл. После reboot четыре сервиса
healthy; фильтр поднялся раньше Docker, маркер сохранился. Пакетная проверка
вне подсети снова дала timeout8080, connected22 и увеличение DROP на 2.

Сохранность проверена до добавления новых браузерных данных: 22 пользователя,
20 видео, по 10 лайков/комментариев/плейлистов, 6 grants; хеши всех 40 MP4/JPEG,
паролей и остальных несетевых настроек .env, demo manifest совпали. При повторе
совпали уже все байты .env, PID dockerd не изменился. Хеши 14 файлов SSH/UFW/
Docker daemon совпали; UFW остался inactive. Финальный опубликованный адрес —
`http://192.168.1.16:8080`, разрешённый источник — `192.168.1.0/24`.

## Основные функции через LAN в Chrome

Команда из корня проекта на другом компьютере, без host networking:

```bash
mkdir -p .artifacts/lan-browser
docker run --rm --init --pids-limit 1024 --shm-size 256m \
  --memory 2g --cpus 2 --read-only --tmpfs /tmp:size=512m,mode=1777 \
  --cap-drop ALL --security-opt no-new-privileges:true \
  -e PYTHONPATH=/tests/browser \
  -e FOXTUBE_TEST_BASE_URL=http://192.168.1.16:8080 \
  -e FOXTUBE_BROWSER_ARTIFACTS=/artifacts/lan-browser \
  -v "$PWD/tests:/tests:ro" -v "$PWD/.artifacts:/artifacts" \
  foxtube-browser:local python /tests/deployment/browser.py
```

Использован ранее собранный образ Dockerfile.browser; на Linux каталог артефактов
должен быть доступен UID1000. Chrome **156.0.8078.80**, runner exit0, ошибок
JavaScript **0**. Созданы четыре обычных QA-аккаунта и два синтетических видео;
они остались в приложении отдельно от исходных данных.

|---|---|

## Проверки кода

- `make check`: Ruff, форматирование, mypy, ShellCheck и **186 unit passed**.
  Новые 117 тестов покрывают выбор LAN, .env, Compose, локальный Docker,
  конфликты слушателей, сохранение чужих настроек и распознавание своих правил.
- `make test`: **98 integration passed**, настоящие PostgreSQL/Nginx/FFmpeg.
- `make agents-check`, `make doctor`, `git diff --check`: passed.
  На macOS uv/FFmpeg отсутствуют как необязательные инструменты хоста;
  проверки приложения используют контейнеры.
- Независимое security-ревью скрипта и сетевой конфигурации: открытых
  подтверждённых P0–P3 не осталось в просмотренной области.

При ревью также исправлены две проблемы безопасности: переменные
COMPOSE_ENV_FILES/COMPOSE_DISABLE_ENV_FILE могли подменить эффективную .env;
смена работающего LAN endpoint могла убрать фильтр со старого IP/порта.
Теперь эти ситуации отклоняются до замены правил. Удалённый Docker и чужой
слушатель, включая SSH на нестандартном порту приложения, также отклоняются.

## Доказательства и границы

Безопасные логи и JSON находятся в `.artifacts/lan/`, предыдущие отказы —
в `attempt-01/` и `attempt-02/`; каталог исключён из Git. Секреты, cookies,
реальные приватные медиа и пароли в отчёт и исходный архив не включались.
Доказательства последнего полного прогона: `controller.log` с
`CLEAN_ACCEPTANCE_AND_CURRENT_UPGRADE_PASSED`, `clean-result.json`,
`clean-network-after-reboot.log`, `current-network-after-reboot.log`,
`clean-firewall-source.log`, `current-firewall-source.log`,
`current-after-reboot.log`, HTTP/TCP JSON каждого этапа, `check.log` и
`integration.log`.

Не проверены: чистая Ubuntu 24.04; активный UFW с пользовательскими запретами;
другие firewall/backend Docker, direct routing, несколько LAN, IPv6, смена DHCP IP,
доступ из маршрутизируемой соседней подсети, HTTPS/публичный Интернет,
Safari/Firefox и физическое мобильное устройство. Чужие запреты firewall
автоматизация не отменяет. Полный скан портов и нагрузка на целевых 4 CPU/8 ГБ
не выполнялись. LAN HTTP предназначен для доверенной локальной сети.
В этом браузерном LAN-прогоне отдельно не повторялись lifecycle/edit/delete,
выход/повторный вход, staff/moderation, Swagger Try it out и перемотка указателем/
touch. Их прежние результаты описаны в отчётах 2026-11-04; свежими результатами
этого прогона они не объявляются.

Основания выбора фильтра: Docker описывает обход UFW INPUT опубликованными
портами в [документации firewall](https://docs.docker.com/engine/network/packet-filtering-firewalls/);
атомарное применение — [nftables](https://wiki.nftables.org/wiki-nftables/index.php/Atomic_rule_replacement),
comment правила — [Ubuntu Jammy libnftables JSON](https://manpages.ubuntu.com/manpages/jammy/man5/libnftables-json.5.html).
