# Проверки и приёмка

Реализованы каркас, учётные записи, видео, каналы, социальные действия,
модерация, роли и демо. Фактические результаты и оставшиеся проверки —
в [status.md](status.md). Отдельная [проверка чистой Ubuntu 22.04.5](review-ubuntu-2026-11-04.md)
подтвердила установку, Chrome/private, повтор и перезагрузку ВМ. Проверки в Docker
сами по себе не подтверждают установку на чистую ОС и ёмкость сервера 4 CPU/8 ГБ.

## Действующие команды

```bash
make agents-check
make check
make test
make test-browser
make test-resilience
make test-capacity
```

make check собирает development-образ и запускает Ruff, mypy, ShellCheck и unit-тесты
без сети. Проверяются HTML/экранирование поиска, локальные Swagger-ресурсы и OpenAPI,
Host/заголовки, liveness и отказ readiness при недоступной БД. Отдельно проверяется
cookie для HTTP/HTTPS и анонимной/авторизованной сессии.

make test создаёт отдельный Compose-проект с временными секретами, томами и портом;
после прогона удаляет только его ресурсы. Настоящие PostgreSQL/Nginx/worker проверяют
readiness, запрет прямого GET/HEAD/Range к существующему файлу, ограничения runtime-ролей
и upgrade/check/downgrade/upgrade миграций в отдельной временной БД. SQLite не используется.
Отдельные ошибки инжектируются: например, PermissionError при удалении — через
monkeypatch shutil.rmtree; это не проверка реального отказа файловой системы.
Запуск интеграционных тестов без этого окружения завершается ошибкой, а не skip.

Критичные сценарии auth проверяются в tests/test_auth_integration.py:

- Нормализация email, атомарное создание пользователя/канала, повторная и
  конкурентная регистрация: один аккаунт и один канал, проигравшему 409.
- Хранение хеша токена, сроки, отзыв, ротация и недействительность скопированной
  старой cookie; конкурентная ротация допускает только одного победителя.
- Все auth POST без CSRF/Origin, чужой CSRF, не-ASCII заголовок: отказ без 500.
- Истёкшая сессия, /me и /account без входа, XSS в имени и свежая роль из БД.
- Одинаковые 401 для неверного пароля/неизвестного email; массовое назначение
  role/user_id запрещено, пароль не отражается в ошибке.
- NUL и некорректные Unicode-суррогаты в имени и непредставимый в UTF-8 пароль:
  422 без сохранения аккаунта и отражения пароля в ответе.
- Общие лимиты PostgreSQL, фиксация неудачных попыток, 429/Retry-After;
  выход при заполненном лимите и повторный анонимный выход без новых строк.
- Тело больше 16 КиБ с Content-Length и chunked: 413 на каждом auth POST.
- Права API/worker на реальных подключениях, включая запрет назначения ролей
  и чтения паролей worker. Очистка старых сессий/лимитов выполняется ролью
  worker; действующие и недавно истёкшие/отозванные сессии сохраняются.

Тестовые аккаунты и пароли синтетические; используются настоящие хеширование,
БД и HTTP через Nginx. Тесты не выводят cookie/CSRF/пароли при ошибках.

Дополнительные аргументы pytest: `bash scripts/test.sh -k readiness`.
Запуск и ручные проверки: [development.md](development.md).

Критичные видео-сценарии:

- tests/test_transcode.py запускает настоящие FFmpeg/ffprobe для MP4/WebM,
  Opus, немого/вертикального видео, SAR/поворота и полного декодирования результата.
  Ограничения метаданных проверяются также синтетическими данными ffprobe;
  ограниченные stdout/stderr, остановка/тайм-аут — на дочернем Python-процессе.
  Проверяется отказ без перезаписи существующего артефакта. Два настоящих
  усечённых MP4 (короткий валидный ролик и файл с отрезанными байтами)
  отклоняются проверкой результата; полный контрольный файл принимается.
- tests/test_video_integration.py проверяет потоковую загрузку, ранний отказ
  до тела, переполнение/очистку/повтор целого файла, один черновик, 429,
  идемпотентное принятие и настоящий READY через работающий worker.
  Матрица MP4/превью/GET/HEAD/Range включает владельца, гостя, получателя,
  постороннего, moderator/admin, отзыв, public → private, hidden и deleted.
- tests/test_video_jobs_integration.py использует отдельные настоящие схемы
  PostgreSQL для конкурирующего claim, старой попытки, истечения аренды,
  остановки/повтора, лимита попыток и запрета публикации удалённого видео.
  Реальный файл после восстановления проверяется на диске; hidden/private
  сохраняются. Есть регрессии обхода очистки за первой пачкой из 200 файлов,
  ошибки удаления без освобождения квоты и превышения пользовательской квоты.
  Истечение аренды устанавливается в БД; stop Event установлен до обработки;
  удаление происходит после claim перед прямым finish_attempt без активного FFmpeg.
  Эти проверки не заменяют kill контейнера, потерю БД и удаление при работающем FFmpeg.
- make test-browser создаёт отдельный Compose и Chrome с H.264. Через экран:
  регистрация → отправка настоящего десятисекундного MP4 со звуком → READY →
  воспроизведение → перемотка на седьмую секунду → продолжение → лайк,
  комментарий и плейлист с проверкой сохранения после перезагрузки. После
  загрузки комментариев проверяется скрытие лишней кнопки следующей страницы.
  Другой аккаунт подписывается на канал, открывает ленту подписок и отправляет жалобу.
  Затем администратор назначает ему роль модератора без замены активной сессии;
  через экран проверяются скрытие/восстановление, закрытие жалобы, аудит и
  запрет понижения последнего admin. Гость проверяет HEAD/Range превью и MP4
  после каждого решения. Проверяются лента, поиск и правильное выделение
  собственного канала в меню. Затем владелец загружает приватное видео,
  через экран выдаёт доступ двум аккаунтам и отзывает одному. Отдельные
  сессии владельца, двух приглашённых, постороннего и гостя проверяют HTML,
  API, списки/счётчики/публичный плейлист и MP4/превью GET/HEAD/Range.
  Приглашённые действительно воспроизводят и перематывают H.264; после
  отзыва второму сохраняется доступ. Через Swagger Try it out создаются
  метаданные, выбирается бинарный файл и выполняется загрузка до READY
  с последующим воспроизведением. Раскрытые curl-примеры с CSRF не снимаются.
  Затем `tests/browser/lifecycle.py` проверяет обычный выход/вход и неверный пароль,
  сохранение состояния, изменение заголовка/описания и public/private/public,
  отмену лайка и удаление своего комментария. Отписка сохраняется и убирает канал
  из ленты. Плейлист переименовывается и закрывается от гостя, один элемент
  удаляется отдельно; удаление плейлиста сохраняет исходные видео. В конце
  удаляется первоначальное видео: оно исчезает из студии/поиска и больше
  не выдаётся владельцу/гостю через HTML/API/MP4/превью GET/HEAD/Range.
  Изменения проверяются после reload. Ошибки закрытия браузера также завершают
  runner неуспешно; сообщение об успехе появляется только после очистки.
  Учётная запись первого admin создаётся через API, роль — привилегированной
  CLI-командой только в одноразовом тестовом окружении; встроенного admin нет.
  Снимки 1440×900 и 390×844 просматриваются отдельно. Нельзя считать
  успешный HTTP или readyState доказательством воспроизведения: требуется
  продвижение currentTime до и после перемотки. Отчёт — .artifacts/video-browser.
  `tests/browser/player.py` дополнительно проверяет собственные controls:
  Play/пауза/перемотка ползунком мышью и клавиатурой, mute/громкость/fullscreen,
  restart, скрытие/возврат панели во время просмотра и нативный fallback
  без JavaScript/при недоступном компоненте.
  Отдельный контекст 390×844 с touch проверяет tap play/pause/seek; это эмуляция,
  физическое мобильное устройство не проверяется. Предпросмотр миниатюры проверяется
  по реальному продвижению времени и двум циклам первых 20%, без MP4-запроса
  до наведения; уход выгружает video, reduced motion/Save-Data запрещают autoplay.
  Проверяются точный SVG сайта на прозрачной кнопке, аватар/длительность карточки,
  значок mute и движение/сброс видимой полосы предпросмотра.
  Удержанный настоящий media-запрос проверяет waiting→playing, два снимка
  индикатора — анимацию при текущем CSP и статичный PNG при reduced motion.
  Отдельно инжектируются отказ play(), media HTTP404, PATCH422 и задержка
  HTML-навигации; эти проверки ошибок не выдаются за сбой реальной сети.
  Снимки плеера и предпросмотра сохраняются рядом с общим отчётом.

Каналы и социальные функции проверяются на настоящем PostgreSQL:

- `tests/test_channel_integration.py`: публичное/приватное/скрытое видео,
  grant/отзыв, счётчики до пагинации, отсутствие email и canonical redirect.
- `tests/test_social_integration.py`: сохранённые лайки/комментарии,
  идемпотентность и гонки, CSRF/Origin, чужие объекты, XSS, лимиты;
  подписки/лента и публичные/приватные плейлисты. Отзыв grant во время ожидания
  блокировки не позволяет использовать старое разрешение; недоступные элементы
  исключаются до выдачи и подсчёта. Удаление комментария не раскрывает чужой
  приватный ролик через различающиеся ответы.
- `tests/test_moderation_integration.py`: первый admin, жалобы/решения/аудит,
  скрытие/восстановление и запрет медиа, роли без обхода приватности,
  конкурентное понижение последних администраторов, отзыв роли при ожидании,
  откат действия при отказе записи аудита, SQL-права runtime и некорректный ввод.
- `tests/test_video_integration.py`: также проверяет 422 для NUL/суррогатов
  в метаданных и NUL в API/HTML-поиске через Nginx вместо ошибки PostgreSQL.

`tests/test_demo_integration.py` запускает настоящий `python -m app.demo`:
6 аккаунтов, 12 READY с MP4/превью, 6 комментариев и 6 плейлистов. Повторный
запуск не создаёт дубликатов и не меняет посторонние аккаунты; третий запуск
не восстанавливает вручную удалённый комментарий. После первых двух запусков
проверяется отсутствие активных пользовательских демосессий. Роль администратора демо
не выдаёт. `tests/test_demo_unit.py` проверяет права и повтор manifest,
блокировку параллельного запуска, запрет symlink/FIFO и точную границу
внутренней cookie-policy для Secure cookies. Демо-видео — синтетический
FFmpeg-сигнал, прошедший реальную загрузку и обработку, а не ответ-заглушка.

## Выбор проверки

| Изменение | Достаточная проверка |
|---|---|
| Инструкции/обвязка | Валидатор, рабочие ссылки, загрузка конфигурации Codex |
| Правила/сервис | pytest по изменённому поведению и регрессия исходного дефекта |
| Запросы/модель | Настоящий PostgreSQL, ограничения, доступность и миграция с нуля/с предыдущей схемы |
| Авторизация/права | Матрица из security.md, CSRF, IDOR и независимое ревью |
| Медиа/worker | Настоящие FFmpeg, PostgreSQL и Nginx; сбой и повтор, реальный MP4 |
| Экран | Браузерный сценарий, ошибки/пустые состояния, 1440×900 и 390×844 |
| Развёртывание | Чистая Ubuntu без Docker, один bootstrap, повторный запуск и перезапуск |

Не использовать SQLite вместо PostgreSQL, прямой ответ API вместо Nginx
или заглушку кодирования в проверках, подтверждающих работу этих компонентов.
Моки допустимы в unit-тесте отдельной ветви, если интеграционная граница проверена отдельно.

Для аудита зафиксированных runtime Python-зависимостей после `make check`:

```bash
docker run --rm --read-only --tmpfs /tmp:rw,nosuid,size=128m \
  --env UV_CACHE_DIR=/tmp/uv-cache foxtube-dev:local sh -c \
  'uv export --frozen --no-dev --no-emit-project --format requirements-txt --output-file /tmp/runtime-requirements.txt >/tmp/export.log && pip-audit --disable-pip --no-deps --progress-spinner off --cache-dir /tmp/pip-audit -r /tmp/runtime-requirements.txt'
```

Аудиту нужен интернет. Он не проверяет dev/browser-пакеты, ОС, образы или
vendored JavaScript и не заменяет ревью приложения.

## Chrome на установленной Ubuntu

`tests/deployment/browser.py` проверяет уже установленный runtime: регистрация,
канал, UI-upload, настоящий FFmpeg, воспроизведение/seek, социальные действия
и private с двумя получателями и выборочным отзывом. Администратор и отдельный
Compose-проект не требуются. Сценарий создаёт четыре обычных аккаунта и два
синтетических видео; они остаются в приложении. Пароли существуют только в памяти.
Запускайте из корня проекта против выделенной тестовой ВМ. Для LAN-адреса
контейнер Chrome может работать на другом компьютере без host networking:

```bash
docker build -f Dockerfile.browser -t foxtube-browser:ubuntu .
mkdir -p .artifacts/lan-browser
docker run --rm --init --pids-limit 1024 --shm-size 256m \
  --memory 2g --cpus 2 --read-only --tmpfs /tmp:size=512m,mode=1777 \
  --cap-drop ALL --security-opt no-new-privileges:true \
  -e PYTHONPATH=/tests/browser \
  -e FOXTUBE_TEST_BASE_URL=http://192.168.1.16:8080 \
  -e FOXTUBE_BROWSER_ARTIFACTS=/artifacts/lan-browser \
  -v "$PWD/tests:/tests:ro" -v "$PWD/.artifacts:/artifacts" \
  foxtube-browser:ubuntu python /tests/deployment/browser.py
```

На Linux каталог результатов должен быть доступен UID1000 контейнера. Для
loopback-target используйте `--network host` на Linux и точный origin localhost.
Runner принимает base origin только на loopback/RFC1918 IPv4, без публичных доменов;
PUBLIC_ORIGIN установленного приложения обязан совпадать с выбранным адресом.
Снимки и безопасный JSON — `.artifacts/lan-browser/`.

Перед браузером с другого компьютера в LAN выполните проверку HTTP и портов:

```bash
python3 tests/deployment/network.py --base-url http://192.168.1.16:8080 \
  --output .artifacts/lan/network.json
```

Проверяются readiness, главная, Swagger, доступность TCP8080/22 и недоступность
5432/6379/8000. Это проба стандартных портов, не полный скан и не проверка
внутренних socket: отдельно сверяйте итоговые Docker mappings и nft rules.
Для нестандартного порта приложения проверяйте его отдельно. Проверка ничего
не устанавливает, не меняет SSH/firewall и не использует proxy.

LAN-приёмка дополнительно требует: повтор bootstrap без изменения .env/данных,
reboot с автоматическим поднятием фильтра и приложения, внешний запрос из LAN,
отказ источнику вне подсети и неизменность SSH/UFW. Unit-тесты выбора адреса,
настроек и защитных отказов не заменяют эти испытания на настоящей Ubuntu.
Выполненные проверки и найденные ошибки — [отчёт LAN](review-lan-2026-11-05.md).

Для каждой попытки установки
после отказа нужен автоматический возврат внешним контроллером к полному снимку
ВМ, затем сверка исходных пакетов/настроек. Протокол отката описан в
[development.md](development.md#испытания-на-чистой-ubuntu-и-откат), выполненные
попытки — в [отчёте Ubuntu](review-ubuntu-2026-11-04.md).

Ошибка даже после выполнения сценария, включая `Browser.close()`, должна
перевести отчёт в failed и дать ненулевой код завершения. Регрессия с реальным
Chrome и контролируемым исключением после штатного закрытия, а затем обычный
успешный запуск выполнены на Ubuntu: [отчёт процессов](review-workflows-2026-11-04.md).
Такие проверки установленного runtime создают тестовые данные и не являются
повторными попытками установки ОС/проекта.

## Автоматизация

- Ruff check и format --check; mypy для прикладного Python-кода.
- pytest: unit, integration и e2e разделены. HTTPX проверяет API; данные/тома тестов изолированы.
- Playwright для Python с channel=chrome в отдельном тестовом окружении. Chrome с H.264 устанавливается туда, не поверх браузера пользователя.
- Проверки браузера ждут состояние через polling/локаторы, без случайных sleep и автоматического пропуска при отсутствии кодека.
- docker compose config и nginx -t; ShellCheck для bootstrap/других содержательных shell-скриптов.
- Зафиксированные зависимости проверяются pip-audit перед поставкой. Находки оцениваются по применимости; бессрочно глушить их нельзя.
- Команды каркаса, видео и браузера оформлены в Makefile; без фиктивных зелёных наборов.

## Негативные и аварийные сценарии

- Повреждённый/ложно названный/слишком большой файл, превышение длительности/разрешения, видео без звука, поворот и вертикальный кадр.
- Отмена передачи и зависшая загрузка: файлы/резерв освобождаются; превышение квоты/очереди/диска не оставляет мусор.
- Конкурирующие загрузки не обходят лимиты. API не буферизует весь файл в RAM.
- Остановка worker/FFmpeg, истёкшая аренда, потеря БД и повтор: нет дубликатов, чужой попытки READY и частично опубликованных файлов.
- Скрытие/удаление во время обработки не отменяется worker. Public → private и отзыв закрывают новые медиа-запросы.
- Запросы без авторизации/CSRF, изменение чужого объекта/роли, обход файловых путей; ACL проверяется также в списках и счётчиках.
- Для файла длины L: допустимый одиночный bytes-диапазон — 206 с Content-Range; синтаксически корректный диапазон за концом файла — 416 с Content-Range: bytes */L. HEAD не отправляет тело.
- Malformed Range и неизвестная единица обрабатываются штатно Nginx, без 5xx и обхода ACL; не требовать 416 во всех случаях и не писать свой парсер. Основание: [RFC 9110 §14.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-14.2).
- Выдача по точному email зарегистрированного аккаунта и отзыв работают только у владельца; неизвестный email, повторная выдача и попытка другого пользователя не создают лишних разрешений.
- Повторные bootstrap/seed сохраняют секреты/данные; демо не зависит от внешних видеоссылок.

## Нагрузка и отчёт

`make test-resilience` создаёт собственные временные конфигурацию и тома.
Реальный SIGKILL worker подаётся при обнаруженном FFmpeg; повтор дожидается
естественного истечения аренды. Затем проверяются остановка БД при кодировании
скрытого private-видео, удаление при активном FFmpeg и остановка/запуск всех
четырёх сервисов. Проверяются отсутствие дублей публикации, освобождение квот,
сохранение private/hidden, сессий и SHA-256 готового MP4 через Nginx.
Остановка контейнера БД не моделирует повреждение диска.

`make test-capacity` использует такую же изоляцию. Одновременно идут две
загрузки, настоящий FFmpeg и десять HTTP-зрителей с 64-КиБ Range каждые
200 мс. Один вход — ровно 500 МиБ: настоящее видео с MP4 free box,
без выделения всего тела в памяти клиента. RSS Python-процессов API
измеряется через /proc до и во время передачи; проверяются ограниченный
рост памяти и READY всех роликов. Это локальный smoke-прогон, без доказательства
максимальной ёмкости, десяти браузеров или внешнего сетевого канала.
Отчёты — `.artifacts/resilience/report.json` и `.artifacts/capacity/report.json`.
Для этих двух команд дополнительно нужен Python 3 на хосте.

На сервере 4 CPU/8 ГБ проверить две передачи, одно кодирование и десять просмотров;
генератор нагрузки работает отдельно. Измерить CPU, RAM, задержки API и исходящий трафик.
Нет OOM/необработанных 5xx; память API не растёт с полным размером входа.
Не заявлять SLA/ёмкость сервера без измерений. Не запускать тяжёлые прогоны параллельно.

Для каждого прогона: команда, окружение, passed/failed/blocked, доказательство и дефект.
Пропущенные/невозможные проверки явно перечисляются. Временные трассы/логи/снимки —
в .artifacts без секретов, безопасные итоговые результаты — в документации этапа.
