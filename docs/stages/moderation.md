# Модерация и управление ролями

Вертикаль по TestTask.md: зарегистрированный зритель отправляет жалобу на
доступное готовое видео; модератор рассматривает её, скрывает или восстанавливает
ролик и закрывает жалобу с причиной. Администратор назначает роли существующим
аккаунтам и читает журнал действий. Данные сохраняются в PostgreSQL.

## Пользовательские действия

- На странице просмотра — раскрываемая форма «Пожаловаться на видео». Нужны
  вход, готовое видимое видео и право просмотра. Для одного зрителя и видео
  допускается одна открытая жалоба; после её закрытия возможна новая.
- `/moderation` — открытые и закрытые жалобы с пагинацией. Скрытие видео и
  закрытие жалобы — отдельные действия с обязательной причиной.
- `/admin` — поиск аккаунта по точному email или ID, смена роли и журнал.
  Частичный поиск email и массовая выгрузка пользователей не предоставляются.
- Роли и решения применяются к следующим запросам сразу из БД, без повторного
  входа. Уже переданные байты отозвать нельзя.

## Границы доступа и транзакций

Приватность, `moderation_status` и состояние обработки независимы. Скрыть можно
также ещё обрабатываемую загрузку. Worker не получает право менять модерацию;
восстановление не делает приватное видео публичным и не ставит READY.
Удалённое автором видео восстановить этой функцией нельзя.

Служебная карточка жалобы показывает ID, состояния и текст жалобы. Если общий
`readable()` запрещает просмотр, вместо названия отображается «Недоступное
видео»; ссылка просмотра отсутствует. Карточка не содержит email автора или
заявителя, ключей хранения, превью или MP4. Moderator/admin без разрешения
владельца не получают приватные байты, включая GET, HEAD и Range.

У API нет прямого UPDATE для `users.role` и `videos.moderation_status` и нет
INSERT/UPDATE/DELETE журнала. Запись выполняют четыре PostgreSQL-функции
SECURITY DEFINER с фиксированным search_path и квалифицированными таблицами.
PUBLIC EXECUTE отозван; EXECUTE предоставлен только `foxtube_api`. Worker не
читает жалобы и аудит и не вызывает эти функции. Все значения параметризованы.

Изменение роли, модерация и закрытие жалобы используют одну короткую advisory
транзакционную блокировку. После неё функция заново проверяет роль исполнителя
из PostgreSQL. Поэтому запрос, ожидавший блокировку, не сохраняет старое право
модератора после понижения. Проверка последнего администратора, изменение роли
и запись аудита проходят в одной транзакции. Конкурентные понижения не оставляют
систему без администратора.

Жалоба сначала блокирует видео, затем отдельным SQL statement заново проверяет
ACL: отзыв grant во время ожидания не остаётся в старом снимке READ COMMITTED.
Частичный уникальный индекс защищает от дубля открытой жалобы под гонкой.
Лимит отправки — 20 попыток на пользователя за 15 минут, общий в PostgreSQL.
JSON/CSRF/Origin и ограничения длины проверяются сервером. NUL и некорректные
Unicode-суррогаты в причинах и решениях отклоняются с 422 до обращения к БД.
Пользовательский текст экранируется в Jinja; JavaScript использует textContent.

Журнал содержит создание и закрытие жалобы, скрытие и восстановление видео,
смену роли и первичное назначение администратора. Каждая запись фиксируется в
той же транзакции, что действие. Повторное скрытие уже скрытого видео и
повторная установка той же роли не создают фиктивное событие. Журнал сохраняет
ID целей после их удаления; email, пароли, cookies и пути файлов туда не пишутся.
Это защита от runtime-изменения истории; привилегированный DBA остаётся доверенным.

## Первое назначение администратора

1. Запустить проект и зарегистрировать собственный аккаунт обычным способом.
2. На сервере выполнить команду через сервис миграций, указав точный email:

   ```bash
   docker compose --profile tools run --rm migrate \
     python -m app.moderation.bootstrap --email owner@example.com
   ```

3. Открыть `/admin` под назначенным аккаунтом и при необходимости назначить
   модератора или второго администратора.

Команда работает только с привилегиями БД для миграций/администрирования и
только пока администраторов нет. Она назначает роль существующему аккаунту
с точным нормализованным email. Изменение и аудит атомарны и используют ту же
блокировку, что HTTP-смена ролей. Runtime API/worker, неизвестный аккаунт и
повторный запуск отклоняются. HTTP bootstrap, пароль по умолчанию и встроенный
администратор отсутствуют. Пароль пользователя команда не меняет.

## API

| Метод и путь | Доступ / действие |
|---|---|
| `POST /api/v1/videos/{id}/reports` | Зритель с ACL; `{reason}` |
| `GET /api/v1/moderation/reports?status=open&page=1` | Moderator/admin; `status=resolved` для закрытых |
| `GET /api/v1/moderation/reports/{id}` | Moderator/admin; безопасная служебная карточка |
| `POST /api/v1/moderation/reports/{id}/resolve` | Moderator/admin; `{resolution}` |
| `PATCH /api/v1/moderation/videos/{id}` | Moderator/admin; `{status: hidden\|visible, reason}` |
| `GET /api/v1/admin/users?email=exact@example.com` | Admin; точное совпадение; вместо email допустим `user_id` |
| `PATCH /api/v1/admin/roles` | Admin; `{email, role, reason}` или `{user_id, role, reason}` |
| `GET /api/v1/admin/audit?page=1` | Admin; пагинация журнала |

Изменяющие API требуют сессию, Origin и CSRF. Лишние поля запрещены. Лимит
страницы — 20 записей; списки строятся пакетно, без отдельного запроса на видео
каждой жалобы. Блокировка ролей не охватывает чтение страниц, загрузку файлов,
обработку видео или раздачу медиа.

## Проверки этапа

Проверено 4 ноября 2026 в отдельной рабочей копии:

- `bash scripts/check.sh` в development-образе с исходниками рабочей копии:
  Ruff, форматирование, mypy, ShellCheck и **32 unit-теста прошли**.
- `bash scripts/test.sh tests/test_moderation_integration.py -q`:
  **12 интеграционных тестов прошли** за 15,34 с, миграции применились с нуля;
  тестовые контейнеры и тома удалены после проверки.
- Независимое ревью проверило новые SQL-функции, API, CLI, карточки и формы.
  Найденные гонка ACL после ожидания, ошибка Jinja dict.items и некорректный
  Unicode во входе исправлены и покрыты прошедшими проверками.

Тесты `tests/test_moderation_integration.py` используют настоящий PostgreSQL,
два API-процесса, Nginx, worker и реальный FFmpeg, без подмены ответов:

- начальный admin только через привилегированную команду и только один раз;
- конкурирующие жалобы, закрытие с решением, повторная жалоба и события аудита;
- скрытие/восстановление настоящего видео и запрет новых GET/HEAD/Range;
- отсутствие приватного названия, email и медиа в служебной карточке и HTML;
- отзыв grant во время ожидания отчёта и отзыв роли во время ожидающей мутации;
- обработка реального файла после скрытия с сохранением private/hidden;
- конкурентное понижение последних администраторов;
- CSRF/Origin, роли, точный email, неизвестные цели и некорректный ввод;
- отклонение NUL и некорректных Unicode-суррогатов на четырёх изменяющих API;
- ограничение PostgreSQL запрещает закрытую жалобу с NULL вместо решения;
- ограничения SQL runtime и откат изменения при невозможности записать аудит.

Ограничения этой отдельной проверки: HTML страниц проверен через настоящий
HTTP, отправка новых JavaScript-форм в Chrome ещё не проверялась; включение
partial в watch и общих ссылок выполняет главный агент. Полный объединённый
roadmap, стилизованный плеер и чистая Ubuntu этим запуском не проверялись.
Pytest сообщает существующее предупреждение Starlette о будущем отказе от
`httpx` в TestClient; проверкам оно не мешает.

## Интеграция отдельной ветки

В изолированной ветке временный родитель `0005_moderation` —
`0003_video_pipeline`. При объединении главный агент устанавливает
`down_revision = "0004_social"`, сохраняя линейную историю миграций.
Главный агент добавляет ссылки `/moderation` и `/admin` в общее меню и включает
`moderation_report.html` в `watch.html`; partial и экраны самостоятельно
подключают `moderation.css`/`moderation.js`. Общий JSON body cap должен включать
`/api/v1/moderation` и `/api/v1/admin` вместе с существующим `/api/v1/videos`.
